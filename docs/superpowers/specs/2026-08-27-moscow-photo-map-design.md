# Дизайн: карта инстаграмных мест Москвы

**Дата:** 2026-08-27
**Статус:** утверждён пользователем в чате, ожидает финального ревью спеки
**Контекст:** домашнее задание №2 курса по AI-агентам (см. `04 · Домашнее задание №2.md`).
Обязательно: работающий результат, работа субагентами, повторяемый workflow.
Дополнительно берём: git worktrees, изоляция/песочница, инъекция недоверенного текста.

---

## 1. Назначение и объём

Небольшой сервис для тех, кто ищет красивые места Москвы для фотосъёмки и/или
ищет фотографа (или сам им является). Без регистрации можно пользоваться почти
всем; регистрация открывает персональный функционал (избранное, мудборды,
сохранённые маршруты) и снимает дневные лимиты на создание контента.

**В объёме MVP:**
- интерактивная карта курируемых + пользовательских мест;
- построение маршрута по нескольким точкам с оценкой времени и сложности;
- открытие/шаринг маршрута по ссылке без входа;
- общая лента заявок на фотосъёмку (роль выбирается при создании заявки);
- личный кабинет: роль профиля, избранное, мудборды, свои маршруты;
- добавление места пользователем (с лимитом и меткой источника).

**Вне объёма (сознательно):**
- модерация пользовательских мест (публикуются сразу, без очереди на проверку);
- прямые сообщения/чат между заказчиком и фотографом (только лента заявок);
- оплата, платёжные интеграции;
- полноценный TSP-оптимизатор маршрута (используется эвристика ближайшего
  соседа — см. §6);
- мобильное приложение, push-уведомления.

## 2. Роли и доступ

| | Гость (без входа) | Зарегистрированный |
|---|---|---|
| Смотреть карту, места, ленту заявок | да | да |
| Строить и открывать/шарить маршрут по ссылке | да | да |
| Добавить место | да, 1/сутки, публикуется сразу с меткой «от пользователя» | да, 5/сутки |
| Создать заявку фотографу | да, 1/сутки | да, 5/сутки |
| Избранное, мудборды, «мои маршруты», кабинет | нет | да |

При достижении лимита гостю показывается ненавязчивое сообщение:
«Войдите, чтобы добавлять до 5 в день» — не блокирующий модал, а строка под
формой.

Роль профиля («я фотограф» / «я ищу фотографа») хранится в профиле
зарегистрированного пользователя как **предпочтение по умолчанию** для его
кабинета, но не привязана жёстко к заявке: при создании заявки роль
выбирается заново (это касается и гостей, у которых профиля вообще нет) —
человек может один раз искать фотографа, а в другой раз предлагать свои
услуги.

## 3. Технический механизм лимитов (без бэкенда)

Гость получает стабильный `auth.uid()` через **Supabase Anonymous Sign-In**
(`signInAnonymously()`), вызываемый прозрачно при первом визите — без экрана
входа, без вопроса к пользователю. Supabase сам хранит сессию в
`localStorage`.

Лимиты (1/сутки для анонимных, 5/сутки для обычных аккаунтов) проверяются
**в Postgres**, а не на клиенте:
- BEFORE INSERT триггер на `places` и на `requests`, считающий число строк
  этого автора (`created_by = auth.uid()`) за текущие UTC-сутки;
- порог берётся из `auth.jwt() ->> 'is_anonymous'` (Supabase проставляет этот
  клайм для анонимных сессий);
- при превышении — исключение из триггера, фронт ловит ошибку и показывает
  сообщение из §2.

Это настоящее ограничение на уровне БД (не обходится через DevTools), при
этом не требует своего сервера — только декларативный SQL внутри Supabase,
что соответствует ограничению «без бэкенда».

Функционал, требующий **настоящей** регистрации (не анонимной сессии) —
избранное, мудборды, сохранённые маршруты — защищён отдельной RLS-политикой,
проверяющей `auth.jwt() ->> 'is_anonymous' = 'false'`.

## 5. Данные (Supabase / Postgres)

```
profiles
  id              uuid PK, = auth.users.id
  role            text null check in ('seeker','photographer')  -- предпочтение по умолчанию
  display_name    text
  created_at      timestamptz default now()

places
  id              bigint PK generated always as identity
  name            text not null
  description     text
  lat             double precision not null
  lng             double precision not null
  tags            text[] default '{}'          -- 'крыши','парки','граффити', ...
  photo_url       text
  source          text not null check in ('curated','user')
  created_by      uuid null references auth.users(id)
  created_at      timestamptz default now()

favorites
  user_id         uuid references auth.users(id)
  place_id        bigint references places(id)
  created_at      timestamptz default now()
  primary key (user_id, place_id)

requests
  id              bigint PK generated always as identity
  request_type    text not null check in ('seeking_photographer','offering_photography')
  place_id        bigint null references places(id)
  wanted_date     date
  comment         text
  author_id       uuid references auth.users(id)   -- в т.ч. анонимный uid
  created_at      timestamptz default now()

routes (только для зарегистрированных — "мои маршруты")
  id              bigint PK generated always as identity
  user_id         uuid references auth.users(id)
  title           text
  start_lat       double precision
  start_lng       double precision
  place_ids       bigint[] not null
  created_at      timestamptz default now()

moodboards (только для зарегистрированных)
  id              bigint PK generated always as identity
  user_id         uuid references auth.users(id)
  title           text
  place_ids       bigint[] not null
  created_at      timestamptz default now()
```

RLS: `places` и `requests` — SELECT всем (включая анонимов), INSERT всем с
лимитом из §3; `favorites`/`routes`/`moodboards` — SELECT/INSERT/DELETE
только `auth.uid() = user_id` и только не-анонимным (§3).

Курируемые места (~40 точек по Москве: крыши, парки, стрит-арт, необычная
архитектура) — засеваются через `supabase/seed.sql`, `source = 'curated'`.

## 6. Маршруты: мультиселект, построение, открытие

**Выбор точек.** На карте и в списке мест — переключатель «добавить в
маршрут» на каждой карточке. Внизу экрана — плашка-трей с счётчиком
выбранного и кнопкой «Построить маршрут». Мультиселект не требует входа.

**Точка старта.** Три варианта на выбор пользователя: геолокация браузера
(с запросом разрешения), клик по любой точке карты, либо одно из уже
выбранных мест.

**Алгоритм.** Жадный ближайший сосед: от старта каждый раз выбирается
ближайшая из ещё не посещённых точек. Не полноценный TSP — осознанное
упрощение, для типичного набора точек (до ~15) даёт маршрут, отличающийся от
оптимального на единицы процентов, чего достаточно для пешей прогулки по
городу. Отмечено как допущение, а не скрыто.

**Оценка времени и сложности.**
- расстояние — по прямой между точками (без построения по улицам, у нас нет
  роутинг-сервиса без ключей);
- время = расстояние / 4.5 км/ч (средняя пешая скорость) + 15 минут на
  точку (время на фото);
- сложность: **Лёгкий** — дистанция < 2 км и точек ≤ 4; **Средний** —
  дистанция ≤ 5 км и точек ≤ 7; иначе — **Сложный**.

**Открытие и шаринг маршрута.** Состояние маршрута кодируется в query-параметры
URL (`?start=lat,lng&places=id1,id2,id3`) — маршрут детерминирован (тот же
вход → тот же порядок обхода от алгоритма), поэтому открытие по ссылке не
требует сохранения на сервере и работает без входа. Зарегистрированный
пользователь дополнительно может сохранить маршрут в таблицу `routes`
(«Мои маршруты» в кабинете) одной кнопкой поверх уже построенного маршрута.

## 7. Заявки на фотосъёмку

Общая открытая лента, видна без входа. Карточка заявки: тип (ищу
фотографа / предлагаю съёмку), место (опционально, может быть не привязана к
конкретной точке), желаемая дата, комментарий, автор (аноним показывается как
«Гость»). Создание — форма с лимитом по §2/§3.

Лента — витрина объявлений, не мессенджер (см. «вне объёма» в §1): связь между
заказчиком и фотографом происходит через контакт, который автор сам укажет в
своём комментарии (телеграм, почта и т.п.) — сервис его не проверяет и не
хранит отдельным полем. Отдельной сущности «отклик» или переписки в MVP нет.

## 8. Мудборды

Доступны только зарегистрированным (требуют избранного, которое само по себе
требует настоящего аккаунта). Пользователь выбирает несколько мест из
избранного → сервис собирает коллаж из их фото (CSS grid/canvas на клиенте,
без внешних API генерации изображений) + короткая подпись с тегами
выбранных мест. Сохраняется в таблицу `moodboards`, доступен повторно из
кабинета.

## 9. Разбивка на независимые части (субагенты / worktrees)

Сначала — общий фундамент, **последовательно, не параллелится**:
скелет Vite + React + TS, клиент Supabase, общие TS-типы (Place, Profile,
Request, Route, Moodboard), общий UI-кит (кнопки, карточки, шапка,
роутинг), SQL-схема + RLS + триггеры лимитов + seed мест.

Затем — три параллельных git worktree (обязательный пункт «агенты» +
опциональный пункт «worktrees» закрываются одним и тем же шагом):

1. **`feature/map-routes`** — карта, карточки мест, фильтры по тегам,
   мультиселект, построение и URL-шаринг маршрута (§6).
2. **`feature/cabinet`** — auth (обычный + анонимный), профиль/роль,
   избранное, кабинет, «мои маршруты».
3. **`feature/requests-moodboard`** — лента заявок (§7) и мудборды (§8).

Каждая ветка работает только в своей папке `src/features/<name>/` и не
трогает чужую; общие типы и Supabase-схема уже зафиксированы фундаментом, так
что конфликтов при merge ожидается по минимуму (в основном — точки
подключения роутов/навигации в `App.tsx`).

## 11. Обязательный workflow: «Добавление нового места в каталог»

Реальная повторяющаяся задача именно для этого проекта — им будут
пользоваться и после сдачи курса, каждый раз находя новое красивое место.

**Вход:** фото (файл или URL), примерные координаты или адрес, короткое
описание, теги.

**Шаги:**
1. Если даны координаты — использовать как есть; если адрес — геокодировать
   через Nominatim (OpenStreetMap, без ключа).
2. Проверить дубликаты: найти в `places` точки в радиусе ~100 м (формула
   гаверсинуса) — если есть, предупредить и спросить, добавлять ли всё равно.
3. Сформировать новую строку и добавить в `supabase/seed.sql`
   (`source = 'curated'`), не только вставить напрямую в живую БД — чтобы
   каталог оставался воспроизводимым с нуля.
4. Обновить счётчик/список мест в README.
5. Показать диф и закоммитить с понятным сообщением.

**Формат сохранения:** оформлен и как простой файл `workflow/add-place.md`
(промпт для копирования), и как проектный скилл Claude Code
`.claude/skills/add-place/SKILL.md` (агент подхватывает по описанию,
вызывается `/add-place`).

## 12. Практика сессий (по аналогии с enot-ai-homework-1)

- Файл сессии (`sessions/session-N.md`) создаётся **до** первой правки кода
  в сессии, не после. В HW1 это правило нарушалось и было явно
  зафиксировано как ошибка — причём **дважды** за один проект, то есть один
  раз пойманное и записанное нарушение само по себе не гарантирует, что оно
  не повторится в следующей сессии. Практическое следствие: первым действием
  в любой новой сессии — до чтения кода, до первой правки — создать/открыть
  файл сессии и вписать промпт, который её начал.
- `STATE.md` переписывается в конце каждой сессии целиком (не история, а
  срез "сейчас"): готово / в работе / не начато / известные проблемы /
  следующий шаг.
- `TOOLS.md` — только дополняется: каждая новая зависимость, MCP, скилл,
  включая тупиковые попытки («поставили — не подошло — сняли»).
- Коммиты — на естественных чекпоинтах (конец фундамента, конец каждой
  фичи-ветки, после merge, после ревью), не один огромный коммит в конце.

## 14. Тестирование и приёмка

В ДЗ №1 главным замечанием было полное отсутствие автотестов («тесты — их
нет вовсе», проверено только вручную) и случай, когда `STATE.md` записал
«клавиатурная навигация проверена», а по факту `Tab` не доходил до маркеров
карты — поймал это только независимый аудит с реальным браузером, а не слова
«готово». В этом проекте оба риска закрываются структурно, а не обещанием:

**Автотесты (обязательны, не факультативны):**
- **Vitest** — юнит-тесты на всю чистую логику: эвристика маршрута
  (детерминированность, корректный порядок для тестового набора точек),
  расчёт времени/дистанции/сложности (§6, граничные значения на порогах
  Лёгкий/Средний/Сложный), функция дедупликации мест по радиусу (§11),
  клиентская часть проверки лимитов (§3).
- **Playwright** — минимум два e2e-сценария на golden path: (1) гостевой путь
  «выбрать места → построить маршрут → открыть по ссылке в новой вкладке»,
  (2) клавиатурная навигация до маркеров карты (`Tab`/`Enter`) — это то самое
  место, где в ДЗ №1 расхождение между STATE.md и реальностью обошлось только
  независимым аудитом; здесь это должно быть частью прогоняемого набора,
  а не разовой ручной проверкой.
- И то, и другое — в `app/package.json` как обычные npm-скрипты
  (`npm run test`, `npm run test:e2e`), исполняемые повторно, а не только
  во время разработки.

**Правило доказательства для STATE.md:** любая запись вида «Х проверено» /
«Х работает» должна ссылаться на воспроизводимую проверку — тест из набора
выше, либо (если автотестом не покрыть, напр. визуальный редизайн) — на
конкретный скриншот `claude-in-chrome` с указанием ширины окна и шагов
воспроизведения. Формулировка без ссылки на проверку в `STATE.md` не
принимается — это прямая реакция на находку аудита ДЗ №1.

**Golden path (прогоняется Playwright + вручную через claude-in-chrome,
фиксируется в REPORT.md):**
1. Открыть сайт без входа → видна карта с местами.
2. Выбрать 3+ места, точку старта → построить маршрут → видна полилиния,
   дистанция, время, сложность.
3. Скопировать URL маршрута → открыть в новой вкладке → маршрут тот же.
4. Без входа добавить место → видно на карте с меткой «от пользователя»;
   повторная попытка в тот же день → сообщение о лимите с намёком на вход.
5. Без входа создать заявку → видна в общей ленте; вторая попытка в тот же
   день блокируется.
6. Зарегистрироваться, задать роль → в кабинете пусто; добавить место в
   избранное с карты → появляется в кабинете.
7. Собрать мудборд из избранного → коллаж отображается и сохраняется.
8. У зарегистрированного лимит — 5 в сутки на места и заявки (тот же
   сценарий, что и в п.4/5, с другим порогом).
9. Клавиатурная навигация: `Tab` доходит до маркеров карты и элементов
   формы, `Enter`/`Esc` работают там, где ожидаются.
10. `npm run build`, `npm run lint`, `npm run test`, `npm run test:e2e` —
    чисто.

**Независимый аудит** — отдельный агент/сессия (не fork — по опыту ДЗ №1
именно «ревьюер без унаследованного контекста» поймал расхождение, которое
автор кода не видел), задача которого — не читать код и верить `STATE.md`,
а **эмпирически перепроверить** написанные там утверждения: реально нажать
`Tab`, реально открыть маршрут по сохранённой ссылке, реально проверить
лимит второй попыткой. Отдельная сессия агента-ломателя (тот же принцип
независимости) — по прогону из материалов курса: кривые данные, границы,
повторные отправки, гонки при одновременном создании заявок/мест.

## 15. Допущения

- Расстояния считаются по прямой, не по факту дорожной сети — явно
  обозначено в UI маршрута («примерное время, по прямой»).
- Пользовательские места не проходят модерацию перед публикацией — только
  визуальная метка источника.
- Связь между заказчиком и фотографом — через контакт, который автор сам
  указывает в комментарии к заявке; отдельной сущности «отклик»/переписки
  нет (лента — витрина, не мессенджер).
- Курируемый каталог составляется вручную через тот же workflow добавления
  места (§11), не парсингом внешних источников.

## 16. Уроки из оценки ДЗ №1

Отчёт преподавателя (90/100, `ДЗ №1 Результат.pdf`) по прошлой работе даёт
три конкретных, проверяемых требования к этой:

| Замечание в ДЗ №1 | Что делаем иначе здесь |
|---|---|
| «Автотестов нет вообще, только ручная проверка и аудит» — главная точка роста, недостающий инструмент назван прямо: Vitest + Playwright | Vitest и Playwright — часть стека с первой сессии (§4, §14), а не опциональное дополнение «если останется время» |
| `STATE.md` утверждал «клавиатурная навигация проверена», реально `Tab` не доходил до маркеров карты — поймал только независимый аудит | Правило доказательства для `STATE.md` (§14): утверждение без ссылки на тест/скриншот не принимается; клавиатурная навигация по маркерам — отдельный пункт golden path и отдельный e2e-тест |
| «Дважды отмечено, что файл сессии заведён не до первой правки» | Явное правило-триггер в §12: файл сессии — первое действие новой сессии, до чтения кода |
| «За 40 промптов ни одного собственного требования к проверке качества — направление задавал агент» | Требования к тестированию зафиксированы в этой спеке заранее (§14), а не оставлены на усмотрение хода диалога в момент реализации |

Также отмечены сильные стороны, которые стоит сохранить: аудит отдельным
агентом на другой модели и **не через fork** (fork наследует контекст автора,
а ревьюеру нужен взгляд без него) — этот же принцип используется в §14 для
независимого аудита и агента-ломателя; фактическая проверка внешнего
источника перед тем, как предлагать его пользователю — здесь так же:
`supabase/seed.sql` и геокодинг через Nominatim проверяются реальным
запросом при первой настройке, а не берутся на веру из документации.
