## Foundation — 100% готово (main)

Все 16 задач + финальный сквозной ревью (opus) + фикс-волна. Схема
Supabase, RLS, триггер дневного лимита — применены на живом проекте и
проверены curl'ом. Общая типизированная логика с тестами
(`app/src/lib/route.ts`, `places.ts`, `limits.ts`, `mappers.ts`,
`supabaseClient.ts`), общий UI-кит, `/add-place` workflow+скилл.

**Два живых бага найдены и исправлены на главной ветке после первичного
Foundation-ревью:**
1. RLS-политика на `places` не проверяла `source` — клиент мог обойти
   дневной лимит, притворившись curated-записью. Исправлено (`60d48fc`,
   ранее `90b9b33`), живьём проверено.
2. `isAnonymousSession()` читала `app_metadata.is_anonymous` вместо
   реального поля верхнего уровня `User.is_anonymous` — гость всегда
   определялся как "не гость". Исправлено в той же фикс-волне.
3. **(найдено веткой requests-moodboard, тоже исправлено)** Общий триггер
   `enforce_daily_limit()` падал на КАЖДОЙ вставке в `requests` с
   `42703 record "new" has no field "source"` — `new` в PL/pgSQL это
   RECORD, и обращение к `new.source` в одном `and`-выражении не
   защищено коротким замыканием от типа. Исправлено (`60d48fc`): проверка
   вложена в отдельный `if tg_table_name = 'places' then`. Живьём
   проверено — `requests` работает, `places` не сломался.

**Урок:** все три бага пропущены при первичной live-проверке, потому что
проверялся только happy-path `places`. При добавлении новой похожей
проверки — тестировать оба типа таблиц, а не по аналогии.

**Supabase:** URL и publishable key теперь **осознанно закоммичены** в
`app/.env.example` (не плейсхолдеры) — это publishable-ключ, безопасный
по дизайну (защищён RLS, не секретностью), решение принято, чтобы
проверяющий не регистрировался. Подробности и обоснование — README.md,
раздел "Как запустить" и коммит `3ba07e4`.

1. Гонка: `main.tsx` запускает анонимный вход fire-and-forget при загрузке

2. **Ранее известная, теперь исправленная проблема:** `updateUser()`
   оптимистично отдаёт `is_anonymous: false` в объекте пользователя сразу,
   но JWT текущей сессии остаётся старым до `refreshSession()` — RLS
   читает именно JWT, поэтому первая запись в `profiles` падала. Исправлено
   вызовом `supabase.auth.refreshSession()` сразу после `updateUser()`

   Supabase Auth API (signup → updateUser → refresh-token), сервер

   подстроке) с параграфом анонимного гейта — Playwright бросает
   strict-mode violation мгновенно, без повторов. Заменено на
   `getByRole('heading', { name: 'Кабинет' })` (`dddd622`).

## Правила координации (не нарушать)

- Каждый агент/ветка работает только в своём worktree. `main` трогает
  только контроллер (я), и только для: Foundation-инфраструктуры,
  живых фиксов, требующих доступа к Supabase, и финальной интеграции.
- Codex получает только точечные, самодостаточные брифы через человека;
  не должен трогать `main`, чужие worktree, `app/` в основном
  репозитории. Обнаружено, что это правило один раз нарушалось —
  требует более явного контроля/подтверждения в следующих брифах.
- Модельная экономия: opus только для финального сквозного ревью
  каждой ветки и эскалации фикс-раунда 4-5; haiku — механические
  задачи; sonnet — задачи с реальным суждением. Задачи без кода
  (создание worktree, exit checkpoint) контроллер каждой ветки
  выполняет сам, без диспетча имплементер+ревьюер.
- Живой Supabase — общая инфраструктура для всех трёх веток и Codex.
  Менять `app/supabase/*.sql` можно только на живом проекте через
  контроллера (у субагентов/веток нет доступа к браузеру/БД).
